# P5.6 — Frontend and Client-Side Security

**Branch:** `feat/p5-6-frontend-client-security`  
**Base:** `develop`  
**Goal:** Tighten the browser-side security surface: CSP, XSS, CSRF, auth-state hygiene, and upload validation.

---

## Current State

- `src/lib/security-headers.ts` sets a CSP that allows `'unsafe-inline'` and `'unsafe-eval'` for scripts and `'unsafe-inline'` for styles.
- `src/store/slices/authSlice.ts` persists the user role in `localStorage` via `parts_peddle_user_role`.
- `src/lib/supabase.ts` uses `@supabase/ssr` `createBrowserClient`, so the JWT is stored in cookies; however, the app also reads a role from `localStorage` for UI decisions.
- No `dangerouslySetInnerHTML` usage was found in the codebase.
- Several UI state items (recent searches, catalog view mode, tour status) use `localStorage` for convenience, not security.
- File upload UI does not perform client-side MIME/size pre-validation.
- `vite` is a dev dependency used by Storybook/Vite tooling; `express` is not in `package.json`.

---

## Gaps

1. CSP is permissive (`unsafe-inline`/`unsafe-eval`).
2. `localStorage` role can be tampered by the user, leading to client-side UI inconsistency (not a server bypass, but a UX/security smell).
3. No CSRF tokens for state-changing forms; reliance is on SameSite cookies.
4. Upload UI lacks client-side validation before sending bytes to the server.
5. Third-party image origins (`images.unsplash.com`, `picsum.photos`) are allowed in CSP and Next.js image config without explicit documentation.
6. No branch tests assert CSP header values or auth-state cleanup.

---

## Work Items

### 1. Tighten Content-Security-Policy incrementally

In `src/lib/security-headers.ts`:

- Keep `default-src 'self'`.
- For `script-src`, move from `'unsafe-inline' 'unsafe-eval'` to:
  - `'strict-dynamic'` with nonces for inline scripts where feasible, or
  - Hashes for known inline scripts generated by Next.js.
- For `style-src`, move from `'unsafe-inline'` to `'self'` plus hashes/nonces; document any required inline styles.
- Document every allowed third-party origin:
  - Supabase: `https://*.supabase.co`, `wss://*.supabase.co`
  - Algolia: `https://*.algolia.net`, `https://*.algolianet.com`
  - Images: `https://images.unsplash.com`, `https://picsum.photos`, `https://*.supabase.co`
- Add a branch test that asserts the production CSP does not contain `'unsafe-inline'` for scripts after the migration.

### 2. Remove security-sensitive state from localStorage

- Stop storing `parts_peddle_user_role` in `localStorage`. Instead, derive the role from the server session on load and refresh it via `supabase.auth.getUser()` or a lightweight `/api/me` route.
- Update `AuthSlice`:
  - `userRole` initializes from server context or defaults to `buyer`.
  - `setUserRole` still updates Zustand state but no longer writes to `localStorage`.
  - On logout/expiry, clear the Zustand auth slice.
- Keep non-sensitive UI preferences (recent searches, view mode, tour done) in `localStorage`; mark them clearly as UI-only.

### 3. XSS hardening

- Audit all uses of `dangerouslySetInnerHTML` (none found currently).
- If rich text/markdown is ever rendered, sanitize it with a library like `dompurify` before SSR/client render.
- Validate image URLs before rendering; ensure they match allowed hostnames and protocols.
- Add an ESLint rule or branch test that fails on new `dangerouslySetInnerHTML` usage.

### 4. CSRF protection for state-changing forms

- Prefer Next.js Server Actions for mutations; they are automatically CSRF-protected by the framework when using cookie auth.
- For Route Handler forms that cannot use Server Actions, add a double-submit CSRF token:
  - Server sets a short-lived `csrf_token` cookie (or embeds it in session metadata).
  - Client submits the token in a `X-CSRF-Token` header.
  - Handler compares cookie value to header value.
- Ensure all auth/session cookies use `SameSite=Lax` minimum (already planned in P5.2).

### 5. Client-side upload validation

- In upload UI components, validate file type and size before calling the API:
  - Allowed MIME types: `image/jpeg`, `image/png`, `image/webp`.
  - Max size aligned with server rule (e.g., 20 MB).
- Show immediate feedback; abort the request if validation fails.

### 6. Dependency and supply-chain hygiene

- Verify `vite` is only used as a Storybook build tool; document if it remains.
- Confirm `express` is not in the dependency tree; if present as a transitive dependency, ensure it is not loaded at runtime.
- Run `pnpm audit --production` and address critical/high findings (also covered in P5.5).

### 7. Add branch tests

Under `tests/branch/p5-6-frontend-client-security/`:

- `csp.test.ts` — assert expected CSP directives and allowed origins.
- `auth-state.test.ts` — assert `AuthSlice` does not write role to `localStorage` and clears on logout.
- `xss-prevention.test.ts` — scan source files for `dangerouslySetInnerHTML` and fail if found.
- `upload-validation.test.ts` — assert upload helpers reject invalid MIME types and oversized files.

### 8. Replace temporary `'unsafe-inline'` CSP with nonce-based App Router CSP (follow-up)

During the first production promotion (2026-07-11), CSP was temporarily relaxed to `script-src 'self' 'unsafe-inline'` because `script-src 'self'` blocked Next.js App Router Flight bootstrap scripts and prevented hydration. This work item removes that temporary relaxation.

**Implementation:**

- Generate a unique nonce per request in middleware (`middleware.ts`) or in a root layout.
- Apply the nonce to the `Content-Security-Policy` header.
- Thread the nonce through Next.js so all inline bootstrap scripts receive `nonce="..."`.
- Update `src/lib/security-headers.ts` to remove `'unsafe-inline'` from `script-src` in production.
- Keep `'unsafe-inline'` for `style-src` only if Next.js still requires it; otherwise migrate styles to hashes/nonces as well.

**Acceptance criteria:**

- Production CSP does not contain `'unsafe-inline'` for `script-src`.
- Every page hydrates correctly in Chrome, Firefox, and Safari.
- `tests/security/headers.spec.ts` and `tests/branch/p5-6-frontend-client-side-security/frontend-security.test.ts` assert the absence of `'unsafe-inline'` for scripts.
- Browser security scan (e.g., Lighthouse or Mozilla Observatory) reports no CSP downgrade.
- Smoke tests pass after the change.

## Risks

- Strict CSP can break third-party scripts or inline event handlers; test every page after tightening.
- Removing localStorage role may cause a brief flash of default role on client load; use server-rendered initial state or a loading state.
- Server Actions require careful error handling and progressive enhancement; ensure forms still work with JS disabled where required.
